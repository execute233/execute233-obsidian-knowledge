# WSL2 文件系统

> [!abstract]
> WSL 2 中实际上同时存在两套文件系统：
>
> * Linux 文件系统：`ext4`
> * Windows 文件系统：通常是 `NTFS`
>
> 开发时最重要的原则：
>
> **Linux 工具操作 Linux 文件，Windows 工具操作 Windows 文件。**

---

# 1. WSL 2 中的两套文件系统

WSL 2 中通常会同时看到：

```text
Linux ext4
├── /
├── /home
├── /etc
├── /usr
└── /var

Windows NTFS
├── C: → /mnt/c
├── D: → /mnt/d
└── E: → /mnt/e
```

例如 Windows：

`C:\Users\Ema\project`

在 WSL 中对应：

`/mnt/c/Users/Ema/project`

而 Linux 项目可能位于：

`/home/ema/projects/my-app`

这两种路径虽然都能从 WSL 访问，但底层不是同一个文件系统。

---

# 2. Linux 文件系统

WSL 2 Distribution 的 Linux 文件系统通常存储在虚拟磁盘 `ext4.vhdx` 中，并使用 `ext4` 文件系统。

逻辑上看到的是标准 Linux 目录结构：

```text
/
├── etc
├── home
├── mnt
├── opt
├── root
├── tmp
├── usr
└── var
```

对于开发最重要的是：

`/home/<user>`

例如：

`/home/ema`

通常可以使用：

`~`

表示当前用户 Home。

推荐建立：

```bash
mkdir -p ~/projects
```

以后项目统一放：

```text
~/projects/
├── backend/
├── frontend/
├── ai-agent/
└── docker-demo/
```

---

# 3. Windows 文件系统

Windows 磁盘默认会挂载到 `/mnt`：

| Windows | WSL      |
| ------- | -------- |
| `C:\`   | `/mnt/c` |
| `D:\`   | `/mnt/d` |
| `E:\`   | `/mnt/e` |

例如：

`C:\Users\Ema\Downloads`

对应：

`/mnt/c/Users/Ema/Downloads`

WSL 使用 `DrvFS` 实现对 Windows 文件系统的访问。

---

# 4. 项目应该放在哪里？

这是 WSL 2 开发中最重要的实践之一。

如果主要使用：

* `git`
* `npm` / `pnpm`
* `Python`
* `uv`
* `pip`
* `Go`
* `Rust`
* `Docker`
* Linux 编译工具

推荐：

`~/projects/my-app`

不推荐：

`/mnt/c/Users/<user>/projects/my-app`

Microsoft 明确建议使用 Linux 工具时把项目保存在 WSL 文件系统，以获得更好的文件 I/O 性能。

---

# 5. 为什么 `/mnt/c` 会慢？

假设 Linux 程序访问：

`~/projects`

路径基本是：

```text
Linux Process
    ↓
ext4
```

而访问：

`/mnt/c/projects`

则需要跨越 Windows / Linux 文件系统边界：

```text
Linux Process
    ↓
WSL 文件系统互操作层
    ↓
Windows NTFS
```

大量小文件操作时差距会更加明显，例如：

`node_modules`

`git status`

`npm install`

`pnpm install`

`cargo build`

`pip install`

Docker Bind Mount

Microsoft 当前文档特别指出，把 Linux 项目放在 `/mnt/c` 会产生明显的跨文件系统 I/O 开销。

---

# 6. 一个实用原则

可以直接记：

| 使用场景                            | 推荐位置                |
| ------------------------------- | ------------------- |
| Linux 后端项目                      | `~/projects`        |
| Node.js Linux 开发                | `~/projects`        |
| Python 项目                       | `~/projects`        |
| Docker 项目                       | `~/projects`        |
| Linux Git 仓库                    | `~/projects`        |
| Windows-only 项目                 | `C:\...`            |
| Office / Photoshop 等 Windows 文件 | `C:\...`            |
| 临时跨系统访问                         | `/mnt/c` 或 `\\wsl$` |

不要因为 Windows Explorer 打开 `C:\` 更方便，就把所有 Linux 项目都放进 `/mnt/c`。

---

# 7. Windows 如何访问 Linux 文件？

Windows 可以通过 UNC 路径访问 WSL。

常见：

`\\wsl$\Ubuntu`

也可以使用：

`\\wsl.localhost\Ubuntu`

例如：

`\\wsl.localhost\Ubuntu\home\ema\projects`

Microsoft 当前文档同时支持 `\\wsl$` 和 `\\wsl.localhost`。

---

# 8. 从 WSL 打开 Explorer

在 WSL 中：

```bash
explorer.exe .
```

`.` 表示当前目录。

例如：

```bash
cd ~/projects
explorer.exe .
```

这样可以快速从 Windows Explorer 查看 Linux 项目。

---

# 9. 不要用 Windows 路径直接猜 Linux 路径

Windows：

`C:\Users\Ema\project`

WSL：

`/mnt/c/Users/Ema/project`

路径规则不同：

| Windows    | Linux          |
| ---------- | -------------- |
| `\`        | `/`            |
| `C:\`      | `/mnt/c`       |
| `C:\Users` | `/mnt/c/Users` |

如果需要程序化转换，可以使用 `wslpath`。

---

# 10. `wslpath`

Windows 路径转 Linux：

```bash
wslpath 'C:\Users\Ema\project'
```

得到类似：

```text
/mnt/c/Users/Ema/project
```

Linux 路径转 Windows：

```bash
wslpath -w ~/projects
```

得到类似：

```text
\\wsl.localhost\Ubuntu\home\ema\projects
```

使用 `/` 风格 Windows 路径：

```bash
wslpath -m /mnt/c/Users/Ema/project
```

得到：

```text
C:/Users/Ema/project
```

这在脚本、IDE 插件和跨平台工具中非常实用。

---

# 11. Linux 大小写敏感

Linux 文件系统默认大小写敏感：

`UserService.ts`

和：

`userservice.ts`

是两个不同文件。

Windows 默认通常大小写不敏感：

`UserService.ts`

和：

`userservice.ts`

通常会被认为是同一路径。

因此：

```text
foo.ts
Foo.ts
FOO.ts
```

在 Linux 文件系统中可以同时存在。

---

# 12. 大小写导致的典型问题

例如 TypeScript：

```ts
import { UserService } from "./UserService";
```

实际文件：

`userService.ts`

Windows 环境可能没有立即暴露问题。

Linux / CI / Docker 中可能直接：

```text
Module not found
```

所以跨平台项目建议：

* 文件命名规范统一
* import 路径严格匹配真实大小写
* Git 中避免只通过大小写反复重命名文件

---

# 13. NTFS 目录的大小写行为

`/mnt/c` 对应 Windows 文件系统，其大小写行为和原生 Linux `ext4` 不完全一致。

Windows 支持给目录启用大小写敏感属性，例如管理员 PowerShell：

```powershell
fsutil.exe file setCaseSensitiveInfo C:\Projects\demo enable
```

关闭：

```powershell
fsutil.exe file setCaseSensitiveInfo C:\Projects\demo disable
```

但多数情况下，更好的解决方案不是折腾 NTFS，而是直接把 Linux 项目放在 `~/projects`。

---

# 14. Linux 权限与 `/mnt/c`

在原生 Linux 文件系统：

```bash
chmod 600 id_rsa
```

会按照标准 Linux 权限模型工作。

例如：

```bash
ls -l
```

可能看到：

```text
-rw------- 1 ema ema id_rsa
```

但是 `/mnt/c` 属于 Windows 文件系统，权限最终还受到 Windows ACL 影响。

WSL 默认会根据 Windows 权限计算 Linux 侧看到的权限；也可以通过 `DrvFS metadata` 存储额外 Linux 权限信息。

因此不要默认认为：

```bash
chmod 777 /mnt/c/xxx
```

就能绕过 Windows 权限。

不能。

Windows ACL 仍然是最终限制之一。

---

# 15. `metadata`

默认情况下，Windows 文件通常不会保存完整的 Linux 权限 Metadata。

可以通过 `/etc/wsl.conf` 配置：

```ini
[automount]
options = "metadata"
```

启用后，WSL 可以使用 NTFS Extended Attributes 保存：

* UID
* GID
* mode
* Linux 文件类型信息

Microsoft 文档列出的相关扩展属性包括 `$LXUID`、`$LXGID`、`$LXMOD` 等。

一般开发不需要主动修改这一配置，除非确实需要在 `/mnt/c` 中保持特定 Linux 权限行为。

---

# 16. `/etc/wsl.conf` 的 automount

Windows Drive 的挂载行为可以通过：

`/etc/wsl.conf`

配置。

例如：

```ini
[automount]
enabled = true
root = /mnt/
options = "metadata,umask=22,fmask=11"
```

其中：

| 配置         | 含义                   |
| ---------- | -------------------- |
| `enabled`  | 是否自动挂载 Windows Drive |
| `root`     | Windows Drive 挂载根目录  |
| `metadata` | 支持 Linux 权限 Metadata |
| `umask`    | 默认权限 Mask            |
| `fmask`    | 文件 Mask              |
| `dmask`    | 目录 Mask              |

这属于高级配置，默认行为通常已经足够。

---

# 17. 修改 `wsl.conf` 后

修改：

`/etc/wsl.conf`

之后退出 WSL，在 PowerShell 中：

```powershell
wsl --shutdown
```

重新进入：

```powershell
wsl
```

配置才会在新的 WSL 实例中重新应用。

---

# 18. Symlink

在 Linux 文件系统：

```bash
ln -s target link
```

属于标准 Linux Symlink。

例如：

```bash
ln -s ~/projects/my-app ~/app
```

然后：

```bash
ls -l ~/app
```

对于 `/mnt/c`，Symlink 和 Windows 文件权限、DrvFS Metadata、Windows 应用兼容性之间会更加复杂。

因此依赖大量：

* Symlink
* Unix Socket
* Linux Permission

的项目更应该位于 Linux 文件系统。

---

# 19. Unix Socket

很多 Linux 软件会使用 Unix Domain Socket，例如：

```text
/var/run/...
/tmp/...
```

这些是 Linux 文件系统语义的一部分。

因此：

* Docker
* PostgreSQL
* SSH Agent
* systemd services

这类工具的数据目录不建议随意移动到 `/mnt/c`。

---

# 20. Git 仓库应该放在哪里？

如果 Git 是在 WSL 中运行：

```bash
git clone ...
git status
git commit
```

仓库推荐：

`~/projects/repository`

而不是：

`/mnt/c/Users/...`

原因不仅是性能，还包括：

* 文件权限
* Symlink
* 大小写
* Line Ending
* 文件监听

---

# 21. Git Line Ending

跨 Windows / Linux 开发还需要注意：

`CRLF`

和：

`LF`

Linux 项目通常使用 `LF`。

推荐通过 `.gitattributes` 明确规则，例如：

```gitattributes
* text=auto
*.sh text eol=lf
*.py text eol=lf
*.ts text eol=lf
*.java text eol=lf
```

如果团队有固定规则，以项目 `.gitattributes` 为准。

不要单纯依赖开发机器上的 Git 默认配置。

---

# 22. Docker 项目为什么更应该放 Linux 文件系统？

假设项目：

`/mnt/c/projects/backend`

然后 Docker 将源码 Bind Mount 到 Container：

```text
Windows NTFS
    ↓
WSL
    ↓
Docker
    ↓
Container
```

文件操作需要跨越更多边界。

而：

`~/projects/backend`

通常更接近：

```text
WSL ext4
    ↓
Docker
    ↓
Container
```

因此对于：

* `node_modules`
* Hot Reload
* Vite
* Webpack
* TypeScript Watch
* Python Reload
* 大型 Git Repo

通常体验更好。

Microsoft 也明确将 `/mnt/c` 上运行 Linux 构建工具列为常见性能问题。

---

# 23. Windows 程序访问 Linux 文件也有成本

反方向同样存在跨文件系统开销。

Windows 程序访问：

`\\wsl$\Ubuntu\home\ema\projects`

需要跨越 Windows / Linux 文件系统边界。

所以：

> 不要简单理解成“Linux 文件系统永远更快”。

正确原则是：

**代码放在主要执行工具所在的文件系统。**

例如：

Linux 工具链：

```text
WSL ext4
```

Windows 工具链：

```text
NTFS
```

---

# 25. WSL 2 Linux 数据实际存在哪里？

WSL 2 Distribution 使用虚拟硬盘保存 Linux 文件。

典型形式：

`ext4.vhdx`

可以理解为：

```text
Windows NTFS
└── ext4.vhdx
    └── ext4
        ├── /
        ├── /home
        ├── /usr
        └── /var
```

Microsoft 当前文档仍将 WSL 2 Distribution 描述为使用 VHD 存储 Linux 文件系统。

---

# 26. 不要直接修改 `ext4.vhdx`

不要把：

`ext4.vhdx`

当普通压缩包或数据文件直接编辑。

正常访问 Linux 文件应该使用：

* WSL Shell
* `\\wsl$`
* `\\wsl.localhost`
* VS Code WSL
* `wsl.exe`

磁盘维护、迁移、扩容等操作后面放在：

`[[WSL2磁盘管理]]`

# 27. 文件系统工程实践

推荐：

```text
Windows
│
├── Downloads
├── Documents
└── Windows-only Projects

WSL 2
└── /home/<user>
    ├── projects
    │   ├── java
    │   ├── typescript
    │   ├── python
    │   └── docker
    │
    ├── .ssh
    ├── .config
    └── .local
```

项目：

```bash
~/projects
```

SSH：

```bash
~/.ssh
```

Linux 配置：

```bash
~/.config
```

临时 Windows 文件则直接通过：

```bash
/mnt/c/Users/<WindowsUser>/Downloads
```

访问即可。
