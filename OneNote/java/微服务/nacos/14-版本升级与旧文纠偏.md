# 版本升级与旧文纠偏

升级 Nacos 时要同时核对服务端、客户端、数据库和访问接口，旧教程的可用配置不能直接视为新版的推荐用法。

> [!abstract]
> 本课重点：旧文版本边界；3.2.4 的行为变化；升级前检查和回退限制。

## 常见旧版用法与迁移

旧版命令、配置和原理描述应结合当前版本核对，下面汇总常见差异。

| 旧版用法 / 常见误解 | 当前版本说明 |
| --- | --- |
| Server 使用 JDK 8 即可 | 3.2.4 Server / Console 需要 Java 17 |
| <code>8848/nacos</code> 登录，默认密码 <code>nacos</code> | 默认 Console 为 <code>8080</code>，首次初始化密码 |
| 数据库类型完全由单机 / 集群决定 | 单机也可用外置 MySQL，集群也有内置存储方案 |
| 配置必须放在 <code>bootstrap.yml</code> | 新示例使用 <code>application.yml</code> + <code>spring.config.import</code> |
| <code>shared-configs</code> / <code>extension-configs</code> 拆分配置 | 使用显式的多个 import 条目 |
| Ribbon 负责 Spring Cloud 负载均衡 | 示例使用 Spring Cloud LoadBalancer |
| 所有临时实例都每 5 秒 HTTP 心跳 | gRPC SDK 由连接生命周期维持；HTTP 客户端需续约 |
| 2.x / 3.x 不支持持久服务的订阅 | 不能作为现行通用结论；以当前 SDK 和持久服务发现路径为准 |
| 配置写入必须每个 Server 都保存才算成功 | 外置数据库事务、内置存储多数派、节点缓存通知要分开理解 |
| 直接查询某节点就能说明整体强一致 | 需要区分持久状态、节点缓存和客户端视图 |

官网也可能残留旧例子。对具体默认值，优先查看**选定标签的发行配置**；对 API 和兼容行为，结合该标签源码与 Release Notes。

## 通信机制迁移对照

| 场景 | 1.x 常见机制 | 本课程 Nacos 3 的用法 |
| --- | --- | --- |
| 临时注册与存活 | HTTP 注册、周期心跳 | gRPC SDK 依赖连接生命周期；v3 HTTP 临时注册依赖续约 |
| 服务订阅 | HTTP 获取、UDP 推送、定时查询兜底 | gRPC 订阅与视图推送，重连 Redo |
| 配置监听 | HTTP 长轮询，对比 MD5 | gRPC 监听，接收变更通知后查询内容 |
| HTTP 接口 | v1 / v2 接口与参数 | 新程序使用 v3 Client / Admin API |

旧 SDK 的 UDP 推送可能丢失，因此结合定时查询修正服务视图；这不是 Nacos 3 SDK 的默认通信链路。

历史 HTTP 心跳常见的 5 秒 / 15 秒 / 30 秒，以及资料中的“3 秒连接检查、20 秒无流量”等数值，必须结合具体版本和实现解释，不能当作 Nacos 3 所有客户端的清理时序或统一 SLA。

## 架构、配置与存储迁移

| 旧资料中的内容 | 在 Nacos 3 中怎样处理 |
| --- | --- |
| Sidecar Agent | 不等同于 AI 管理中心的 A2A Agent；DNS / 代理能力按具体生态组件接入 |
| <code>KvStorage</code> 接口示例 | 属于历史架构说明，不是 3.2.4 面向应用的 SDK；应用使用当前 SDK / API |
| <code>config_info_beta</code> / <code>config_info_tag</code> | 新部署使用 3.2.4 SQL 的 <code>config_info_gray</code>；存量灰度按迁移流程处理 |
| <code>bootstrap.yml</code> / <code>bootstrap.properties</code> | 本课程 Alibaba 2025.1 使用 <code>application.yml</code> + <code>spring.config.import</code> |
| 应用名隐式加载、<code>shared-configs</code>、<code>extension-configs</code> | 改成明确的 import 条目，逐条指定资源与刷新选项 |
| 按实例 IP / port 在 HTTP Filter 中转发 | 不能套到全部 gRPC 写请求；Nacos 3 gRPC client state 由连接所属节点维护 |

协议、状态处理器与数据源抽象有不同职责。阅读旧实现时，对照当前源码入口核对，不把历史存储接口随意替换成 Redis 就视为完成新版接入。

## 3.2.4 需要注意的变化

| 变化 | 对学习和运维的影响 |
| --- | --- |
| JRaft 原生 gRPC 验证 Server identity | 全节点设置相同非空 key / value；不是关闭 Client auth 就能绕过 |
| 部分废弃 AI API 默认关闭 | 旧接口可能返回 HTTP <code>410 Gone</code>，迁移到标准接口 |
| MCP 工具导入限制内网 / 本机目标 | 有需要时配置管理员维护的允许列表并重启 Console |
| 独立 Console 的调用身份转发修复 | 后端按真实调用者执行 RBAC，不能依赖过去的越权行为 |
| Prompt 可见性、配置历史等修复 | 验证所用权限和业务流程，不能只检查启动成功 |

## JRaft 强制校验与回退

滚动升级期间，3.2.4 会暂时兼容不能携带 JRaft 凭据的旧节点。当成员列表内所有节点都支持新鉴权后，新进程进入强制校验状态，并持久化状态：

```text
data/jraft-auth-enforced.state
```

> [!danger]
> 强制校验生效后，不能把“逐节点滚回不携带凭据的旧版本”当作可靠回退方案。不要通过删除状态文件恢复兼容。升级前准备并验证与实际数据库、持久数据相配套的回退方案。

Token 密钥和 Server identity 不是自动同步的配置，部署人员需在所有节点维护一致值。

## 兼容开关的边界

| 项目 | 作用 | 不能做什么 |
| --- | --- | --- |
| <code>nacos.core.api.compatibility.enabled=true</code> | 临时重新启用明确接入门禁的废弃 v3 AI API | 不会恢复已从主发行包移除的全部 v1 / v2 API |
| Legacy API adapter | 给特定旧 HTTP API 提供迁移窗口 | 不能假定任意 Server / adapter 版本组合可用 |
| Namespace 兼容 / 迁移 | 处理历史空 ID 与 <code>public</code> 数据 | 不能把旧资源和新资源误认为天然相同 |

新写的脚本使用 v3 API；现有旧系统先盘点调用，再按官方升级文档选择适配器及迁移路径。兼容开关不是长期解决方案。

## 升级检查顺序

1. 记录当前 Server / Console / SDK、Java、数据库和插件版本。
2. 备份数据库及各节点需要的持久化数据、配置文件，并验证恢复。
3. 盘点旧 API、默认命名空间、Beta / Tag 配置、AI 资源和鉴权方式。
4. 在独立测试环境验证目标版本，先统一全节点内部身份。
5. 按该起始版本对应的升级路径逐节点操作，观察集群状态和协议日志。
6. 验证注册 / 订阅 / 重连、配置读取 / 刷新、历史 / 灰度、权限与监控。
7. 完成迁移后关闭临时兼容项，保留可追溯的发布记录。

这些是升级检查顺序，不是所有历史版本都能直接一步升到 3.2.4 的承诺。
