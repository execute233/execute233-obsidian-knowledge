# 运维监控与故障排查

Nacos 排错先确定故障发生在连接、资源身份、权限、持久化还是应用刷新层，再用日志与接口逐层定位。

## 本机检查

```bash
java -version
"$JAVA_HOME/bin/jps" -lv
nc -zv '<NACOS_HOST>' 8848
nc -zv '<NACOS_HOST>' 9848
ss -lntp | grep -E ':(8080|8848|9848|9849|7848)\b'
```

将主机占位符替换为目标地址。日志检查在 Nacos 所在机器上执行，定义 <code>$nacosDir</code> 为读者自己的发行包目录：

```bash
nacosDir='<NACOS_DIR>'
tail -n 100 "$nacosDir/logs/nacos.log"
grep -E 'ERROR|Exception|denied|timeout' "$nacosDir"/logs/*.log
```

## 指标与健康入口

在每个节点的 <code>application.properties</code> 中启用并重启：

```properties
management.endpoints.web.exposure.include=prometheus
```

| 入口 | 用途 |
| --- | --- |
| <code>/nacos/actuator/prometheus</code> | Server 指标抓取 |
| <code>/nacos/v3/admin/core/state</code> | Server 状态 |
| <code>/nacos/v3/admin/core/state/liveness</code> | Server 存活 |
| <code>/nacos/v3/admin/core/state/readiness</code> | Server 是否准备好服务请求 |
| <code>/v3/console/health/readiness</code> | 独立 Console 就绪状态 |

Server 接口使用 Server 主端口，Console 接口使用 Console 端口；按真实上下文路径和接口鉴权规则访问。监控抓取范围限制在内部网络。

```yaml
scrape_configs:
  - job_name: nacos
    metrics_path: /nacos/actuator/prometheus
    static_configs:
      - targets: ['<NACOS_NODE_1_HOST>:8848', '<NACOS_NODE_2_HOST>:8848', '<NACOS_NODE_3_HOST>:8848']
```

<code>nacos.prometheus.metrics.enabled</code> 是 Prometheus 服务发现辅助能力的开关，**不是 Server 指标端点的总开关**。

## 观察什么

| 维度 | 关注指标 / 现象 | 含义 |
| --- | --- | --- |
| JVM | 堆使用、GC 耗时、线程数量 | 判断内存和停顿是否影响连接 |
| HTTP / gRPC | 延迟、失败数、错误码、连接数量 | 判断请求处理与长连接是否异常 |
| Naming | 健康实例比例、订阅者、推送失败 | 判断发现视图与实际运行状态 |
| Config | 发布 / 查询延迟、Dump、监听推送 | 判断从存储到客户端的传播 |
| 数据库 | 连接池、慢 SQL、事务失败 | 判断配置持久化路径 |
| Distro / JRaft | 同步失败、Leader、选举、日志应用 | 判断节点间通信和持久路径 |

指标名可能带 Micrometer 的 <code>_seconds_count</code>、<code>_seconds_sum</code> 等后缀，以实际抓取内容为准，避免直接照搬跨版本 Dashboard。

## 按症状排查

| 症状 | 优先检查 | 常见原因 |
| --- | --- | --- |
| Console 打不开 | <code>8080</code>、启动日志、上下文路径 | 控制台地址填写错误；端口冲突 |
| 页面可登录，Java 连接失败 | <code>8848</code> 与 <code>9848</code>、SDK 错误 | 主端口通但 gRPC 被阻断 |
| 注册不到预期位置 | namespace ID、group、service name | 使用显示名称；环境或分组不同 |
| 能发现但调用失败 | 注册 IP、业务端口、接口路径 | 注册了虚拟网卡 / 回环地址；业务本身异常 |
| 查询少于页面实例数 | enabled、healthy、cluster、保护阈值 | 发现视图经过过滤 |
| HTTP 手工实例很快消失 | 续约和 ephemeral | 只注册一次，没有续约 |
| 重连后实例没恢复 | Redo、连接状态、权限 | 恢复请求失败或 SDK 已关闭 |
| 配置未找到 | namespace、group、Data ID、import | 身份不一致，或配置未发布 |
| 配置发布后接口仍是旧值 | 监听日志、refreshEnabled、Bean 方式 | <code>@Value</code> 所在 Bean 没有刷新；值缓存到普通字段 |
| 配置一直被覆盖 | import 顺序、环境变量、本地 failover | 更高优先级来源或应急覆盖生效 |
| HTTP 403 / access denied | 登录账号、角色、资源读写权限 | Token / 用户存在，但资源授权不足 |
| 节点存活但持久写失败 | 多数派、数据库、身份、JRaft 端口 | 协议通路或持久化路径不可用 |

## 配置不刷新：逐层确认

1. 控制台检查目标 namespace / group / Data ID 的当前内容与历史。
2. 用 Client API 或 SDK 查询相同身份，检查返回的内容与 MD5。
3. 检查应用是否导入了正确条目，且没有关闭动态刷新。
4. 查看监听回调、Spring 刷新相关日志和解析错误。
5. 检查值是否写入静态字段、构造时派生对象或未支持刷新的连接池。
6. 检查客户端 failover、本地快照、环境变量和其他属性来源。

不要直接修改数据库或删除 <code>data</code> 来修复刷新问题；这会绕过发布通知链或损坏持久状态。

## 运维摘流

```text
停止接收新流量 → 确认发现视图和调用方更新
               → 等待在途请求完成 → 停止应用
```

使用控制台禁用实例后，验证消费者实际选择行为。缓存传播和在途请求不是瞬时清零，应用也要支持正常退出和注销。

> [!warning]
> Spring Cloud Alibaba 2025.x 的 Nacos HealthIndicator 默认关闭。若开启，不要直接把受 Nacos 连接波动影响的聚合健康端点用作应用存活探针，否则可能因基础设施抖动反复重启正常应用。
