# 服务模型与实例生命周期

Nacos 用命名空间、分组和服务名确定一个服务，再用实例地址与集群信息描述它的运行节点。

> [!abstract]
> 本课重点：资源身份；临时与持久实例；健康、权重、元数据和订阅恢复。

## 服务身份

```text
Namespace → Group → Service → Cluster → Instance
<DEV_NAMESPACE_ID> → SHOP → service-product → DEFAULT → <INSTANCE_HOST>:9001
```

| 字段 | 含义 | 示例 / 默认 |
| --- | --- | --- |
| <code>namespaceId</code> | 环境或租户隔离；使用 ID | <code>&lt;DEV_NAMESPACE_ID&gt;</code>；3.x 默认 <code>public</code> |
| <code>groupName</code> | 服务分组 | <code>SHOP</code>；默认 <code>DEFAULT_GROUP</code> |
| <code>serviceName</code> | 逻辑服务名 | <code>service-product</code> |
| <code>clusterName</code> | 同一服务的部署集群 | 默认 <code>DEFAULT</code> |
| <code>ip</code> / <code>port</code> | 消费者可访问的业务地址 | <code>&lt;INSTANCE_HOST&gt;:9001</code> |
| <code>metadata</code> | 自定义属性 | 版本、机房、灰度标签 |

Service 的身份是 **namespace + group + serviceName**。调用双方必须对齐身份；同名服务放在不同命名空间或分组中，发现结果不会自动互通。

## 临时与持久实例

| 对比 | 临时实例 <code>ephemeral=true</code> | 持久实例 <code>ephemeral=false</code> |
| --- | --- | --- |
| 典型场景 | Spring Cloud 业务应用 | 需要长期维护地址的基础服务 |
| 状态来源 | 客户端存活和运行时注册 | 服务端持久资源 |
| 存活机制 | gRPC 连接生命周期；HTTP 客户端续约 | 服务端主动健康检查 |
| 异常结果 | 清理运行时实例，重连后 SDK Redo | 通常标记不健康，资源记录保留 |
| 数据同步 | Distro 的 AP 路径 | JRaft 的 CP 持久路径 |

同一 Service 不能混合临时和持久类型。更换 <code>ephemeral</code> 不是无条件更新实例属性：需要先处理已存在的服务与实例，或使用新的服务身份。

## gRPC SDK 生命周期

1. SDK 建立连接，注册实例，服务端记录 publisher。
2. 消费者订阅服务，服务端记录 subscriber 并返回当前视图。
3. 实例变化后，服务端推送新的服务发现视图。
4. 连接断开并被服务端感知后，清理连接维度的发布与订阅状态。
5. SDK 重连成功，通过 Redo 恢复临时注册和订阅。

> [!note]
> 连接健康只能说明客户端连接存活，不能证明商品接口、数据库连接或整个业务链路正常。业务探活、超时与熔断仍需另外设计。

HTTP 临时实例则需要续约。3.x HTTP 注册接口可用 <code>heartBeat=true</code> 表达续约；实例已过期时要重新提交完整注册信息。一次手工注册不代表地址会永久留在列表中。

## 健康、摘流与权重

| 属性 | 表达什么 | 注意点 |
| --- | --- | --- |
| <code>healthy</code> | 健康逻辑认为实例是否可用 | 临时实例和持久实例的判定机制不同 |
| <code>enabled</code> | 是否允许实例参与发现 / 选择 | 运维摘流优先明确禁用并验证消费者行为 |
| <code>weight</code> | 客户端加权选择的权重 | 是否生效由 SDK 或负载均衡实现决定 |
| <code>protectThreshold</code> | 健康实例比例过低时启用保护视图 | 保护视图可能包含实际不健康实例 |

持久实例内置主动检查包括 TCP、HTTP、MySQL 和 NONE：

| 检查类型 | 检查方式 | 能证明什么 |
| --- | --- | --- |
| TCP | 探测目标实例端口能否连接 | 基础网络与监听可达，不能证明完整业务可用 |
| HTTP | 按 Cluster 配置请求探测路径 | 该探测接口是否满足健康判定 |
| MySQL | 按配置连接目标数据库并探测 | 数据库连接 / 探测结果，不代替业务事务验证 |
| NONE | 不执行上述主动探测 | 适合由管理路径手动维护健康状态 |

只有 NONE 检查器场景才适合手动更新持久实例健康状态。探测周期、目标端口和成功条件按 Nacos 3.2.4 的系统参数与 Cluster 配置核对。

当健康比例小于等于保护阈值时，保护视图可以扩大返回的实例集合。它是可用性取舍，**不会修复底层故障**；消费者仍需正确处理调用失败。

## 元数据与负载均衡

| 元数据来源 | 优先级 | 使用场景 |
| --- | --- | --- |
| 应用注册提交 | 较低 | 应用版本、运行环境 |
| 控制台 / Admin API 的运维态覆盖 | 较高 | 临时运维调整、治理标签 |

写入 <code>version=v2</code> 不会自动实现灰度路由；必须让消费者的路由 / 负载均衡策略读取并使用它。改变权重后，也要确认消费者使用了加权策略。

## 查询、订阅和缓存

| 操作 | 行为 |
| --- | --- |
| 查询 | 一次读取当前实例视图 |
| 订阅 | 首次获得视图，之后接收变更 |
| 本地缓存 | 保存最后已知视图，用于恢复和临时容错 |
| Failover | 运维配置的本地发现覆盖，恢复后需退出 |

持久资源与临时注册的恢复路径不同，不能把持久实例也解释成“靠客户端 Redo 恢复”。服务发现缓存可能过期，Nacos 故障时“还能拿到地址”不等于“所有调用仍会成功”。
