# 可靠性

**发送者可靠性**
生产者重连
由于网络波动，可能会出现客户端连接MQ失败的情况，可以使用些配置
spring:
rabbitmq:
connection-timeout: 1s _#_ _重连时间_
template:
retry:
enabled: true _#_ _开启超时重试_
initial-interval: 1000ms _#_ _失败后初始等待时间_
multiplier: 1 _#_ _失败后下次的等待时长倍数_
max-attempts: 3 _#_ _最大重试次数_
注意重试机制是阻塞的，会影响业务性能，建议使用异步

**MQ****可靠性**
在默认情况下，RabbitMQ会将接收到的信息保存在内存中以降低消息收发的延迟。这样会导致两个问题：

- 一旦MQ宕机，内存中的消息会丢失
- 内存空间有限，当消费者故障或处理过慢时，会导致消息积压，引发MQ阻塞

数据持久化
路由持久化、队列持久化都可以在创建时设置
消息持久化可以直接设置消息去
Message message = MessageBuilder._withBody_(bytes).setDeliveryMode(MessageDeliveryMode._PERSISTENT_).build();
Lazy Queue
自RabbitMQ3.12后，所有队列都是LazyQueue模式，无法更改
特征如下：

- 接收到消息直接存入磁盘而非内存
- 要消费时消息才会从磁盘中读取并加载到内存
- 支持百万条消息存储

消息失败处理
失败重试机制
默认情况下消费者出现异常后消息会不断重新入队，再发送给消费者
spring:
rabbitmq:
listener:
simple:
prefetch: 1
retry:
enabled: true _#_ _开启失败重试_
initial-interval: 1000ms _#_ _失败等待时长_
multiplier: 1 _#_ _下次失败等待时长倍数_
max-attempts: 3 _#_ _最大重试次数_
stateless: true _# true__无状态，_ _false__有状态，如果包含事务就得是__false_
重试次数耗尽后，如果依然失败，需要MessageRecoverer接口来处理，有三种不同的实现：
RejectAndDontRequeueRecoverer: 重试耗尽后，直接reject,丢弃消息。默认就是这种方式
ImmediateRequeueMessageRecoverer: 重试耗尽后，返回nack,消息重新入队
RepublishMessageRecoverer: 重试耗尽后，将失败消息投递到指定的交换机
我们可以手动配置
@Bean
public MessageRecoverer messageRecoverer(RabbitTemplate template) {
return new RepublishMessageRecoverer(template, "error.direct", "error");
}
业务幂等性
保证消息的一致性我们可以在定义消息转换器时启用唯一id标识，如
@Bean
public MessageConverter messageConverter() {
Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
converter.setCreateMessageIds(true);
return converter;
}
