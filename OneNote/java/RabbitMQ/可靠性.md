# 可靠性

## 发送者可靠性

### 生产者重连

由于网络波动,可能会出现客户端连接 MQ 失败的情况,可以使用以下配置:

```yaml
spring:
  rabbitmq:
    connection-timeout: 1s        # 重连时间
    template:
      retry:
        enabled: true             # 开启超时重试
        initial-interval: 1000ms  # 失败后初始等待时间
        multiplier: 1             # 失败后下次的等待时长倍数
        max-attempts: 3           # 最大重试次数
```

注意重试机制是阻塞的,会影响业务性能,建议使用异步。

## MQ 可靠性

在默认情况下,RabbitMQ 会将接收到的信息保存在内存中以降低消息收发的延迟。这样会导致两个问题:

- 一旦 MQ 宕机,内存中的消息会丢失。
- 内存空间有限,当消费者故障或处理过慢时,会导致消息积压,引发 MQ 阻塞。

### 数据持久化

路由持久化、队列持久化都可以在创建时设置。消息持久化可以直接设置消息:

```java
Message message = MessageBuilder.withBody(bytes)
    .setDeliveryMode(MessageDeliveryMode.PERSISTENT)
    .build();
```

### Lazy Queue

自 RabbitMQ 3.12 后,所有队列都是 Lazy Queue 模式,无法更改。特征如下:

- 接收到消息直接存入磁盘而非内存。
- 要消费时消息才会从磁盘中读取并加载到内存。
- 支持百万条消息存储。

## 消费者可靠性

### 消费者确认机制

为了确认消费者是否成功处理消息,RabbitMQ 提供了消费者确认机制(Consumer Acknowledgement)。当消费者处理消息结束后,应该向 RabbitMQ 发送一个回执,告知 RabbitMQ 自己消息处理状态。回执有三种可选值:

- **ack**:成功处理消息,RabbitMQ 从队列中删除该消息。
- **nack**:消息处理失败,RabbitMQ 需要再次投递消息。
- **reject**:消息处理失败并拒绝该消息,RabbitMQ 从队列中删除该消息。

### SpringAMQP ACK 处理方式

SpringAMQP 已经实现了消息确认功能。并允许我们通过配置文件选择 ACK 处理方式,有三种方式:

- **none**:不处理。即消息投递给消费者后立刻 ack,消息会立刻从 MQ 删除。非常不安全,建议使用。
- **manual**:手动模式。需要自己在业务代码中调用 api,发送 ack 或 reject,存在业务入侵,但更灵活。
- **auto**:自动模式。SpringAMQP 利用 AOP 对我们的消息处理逻辑做了环绕增强,当业务正常执行时则自动返回 ack。当业务出现异常时,根据异常判断返回不同结果:
  - 如果是业务异常,会自动返回 nack。
  - 如果是消息处理或校验异常,自动返回 reject。

配置:

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: none
```

### 消息失败处理

**失败重试机制**

默认情况下消费者出现异常后消息会不断重新入队,再发送给消费者:

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1
        retry:
          enabled: true             # 开启失败重试
          initial-interval: 1000ms  # 失败等待时长
          multiplier: 1             # 下次失败等待时长倍数
          max-attempts: 3           # 最大重试次数
          stateless: true           # true 无状态,false 有状态,如果包含事务就得是 false
```

重试次数耗尽后,如果依然失败,需要 MessageRecoverer 接口来处理,有三种不同的实现:

```yaml
RejectAndDontRequeueRecoverer:     # 重试耗尽后,直接 reject,丢弃消息。默认就是这种方式
ImmediateRequeueMessageRecoverer:  # 重试耗尽后,返回 nack,消息重新入队
RepublishMessageRecoverer:         # 重试耗尽后,将失败消息投递到指定的交换机
```

我们可以手动配置:

```java
@Bean
public MessageRecoverer messageRecoverer(RabbitTemplate template) {
    return new RepublishMessageRecoverer(template, "error.direct", "error");
}
```

### 业务幂等性

保证消息的一致性我们可以在定义消息转换器时启用唯一 id 标识,例如:

```java
@Bean
public MessageConverter messageConverter() {
    Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
    converter.setCreateMessageIds(true);
    return converter;
}
```
