# unity 目录 markdown 格式审计

## 概况
- 文件总数: 8
- 影响笔记数: 8(全部 8 篇均存在影响渲染的重大偏离)
- 子目录: 脚本开发
- 文件列表:
  1. `脚本开发/transform控制父子.md`(37 行)
  2. `脚本开发/初步认识.md`(8 行)
  3. `脚本开发/场景.md`(50 行)
  4. `脚本开发/按键监听.md`(43 行)
  5. `脚本开发/文件-程序管理.md`(13 行)
  6. `脚本开发/游戏时间.md`(7 行)
  7. `脚本开发/游戏物体的获取.md`(33 行)
  8. `脚本开发/触摸.md`(40 行)

## 全局定性结论
这 8 篇 unity 笔记的"格式骨架"尚未建立:既无标题层级,也无代码块围栏,亦无 frontmatter。所有 C# 代码裸文本暴露在 Markdown 解析器中,直接被解析为普通段落。这意味着代码标识符中的 `**` 和 `_` 会被渲染器误识别为加粗/斜体,并显著影响阅读体验。这是一次"统一格式化"的全局性缺陷,而非个别文件的局部瑕疵。

## 偏离清单

### 高优(影响渲染/可读性)

#### H1. 全部 8 篇缺少 H1 标题(`# `)
- 现象:文件没有任何 `#` 起始的行,仅有文件名充当"标题"。
- 影响:Obsidian 大纲面板为空,内部链接/书签无法锚定。
- 涉及文件:全部 8 篇(`transform控制父子.md`、`初步认识.md`、`场景.md`、`按键监听.md`、`文件-程序管理.md`、`游戏时间.md`、`游戏物体的获取.md`、`触摸.md`)。
- 行内示例:`初步认识.md:1` 直接进入正文 `脚本都继承自MonoBehavior...`,无 H1。

#### H2. 全部 8 篇缺少代码块围栏(` ```cs ... ``` `)
- 现象:全部 C# 代码段都是裸文本段落,没有任何 ``` 围栏。
- 影响:
  - 代码与中文注释混排被当成 Markdown 段落解析。
  - 一旦加上围栏,后续 H3(误识别强调)会自动消失。
  - 无语法高亮。
- 涉及文件:全部 8 篇。
- 行内示例:
  - `transform控制父子.md:1-37` 整篇全是裸代码。
  - `场景.md:1-50` 整篇全是裸代码。
  - `触摸.md:1-40` 整篇全是裸代码。

#### H3. 代码中残留强调符号(会被渲染器误识别)
- `**bold**` 误识别 —— 共 12 处出现在代码标识符里:
  - `transform控制父子.md:1` `void **Start**()`, `:28` `void **Update**()`
  - `场景.md:2` `public class **ScenesTest** : MonoBehaviour`, `:5` `void **Start**()`, `:42` `void **Update**()`
  - `按键监听.md:2` `void **Update**()`
  - `游戏物体的获取.md:2` `public GameObject **Cube**;`, `:4` `public GameObject **Prefab**;`, `:5` `void **Start**()`
  - `触摸.md:1` `void **Start**()`, `:6` `void **Update**()`
- `_italic_` 误识别 —— 25+ 处,典型模式 `Debug._Log_(...)`、`Input._GetMouseButton_(...)`、`SceneManager._LoadScene_(...)` 等函数名被当作斜体。
  - 实例:`transform控制父子.md:4-9` 全部 `._Log_(` 触发。
  - 实例:`按键监听.md:6,11,16,21,26,31` 全部输入 API 触发。
  - 实例:`场景.md:9,11,26,28,35` 全部场景/场景管理器 API 触发。
  - 实例:`触摸.md:14,18,21,24,27,30` 全部 `TouchPhase._Xxx_` 触发。
- 修复路径:套上 ```cs 代码块后,所有 `**`/`_` 都会作为字面字符保留 —— H2 修复后此项"自愈"。

### 中优(结构与可维护性)

#### M1. 全部 8 篇无 frontmatter
- 现象:文件头不存在 `---key: value---` 段。
- 影响:Obsidian 无法识别 `tags`、`aliases`、`cssclass`、`banner` 等元数据。
- 涉及:全部 8 篇。

#### M2. 列表风格缺失 / 文本式条目
- `初步认识.md:2-8` 是典型的"`方法 - 说明`"知识卡片,适合转为 `- **方法** - 说明` 或表格:
  ```
  Awake - 最早调用,用于单例模式
  OnEnable - 组件被激活后调用,在Awake激活后会调用一次
  ```
  当前用纯文本行排列,既无序也无标题分隔。

#### M3. 多语句挤占同一行
- `场景.md:50`: `}   }` —— 两层右花括号挤在一行,中间带 3 个空格(尾空格已清理,合并为一行)。
- `游戏物体的获取.md:11`: `Debug._Log_(o.layer);   Debug._Log_(Cube.name);` —— 两条 Debug 合并在一行。
- `触摸.md:38-39`: `foreach (Touch touch in Input.touches)\n{   }` —— 空 foreach 体挤在一行。

#### M4. 注释中存在轻微口误/一致性问题(非格式但相关)
- `transform控制父子.md:34` `// 绕某个给提旋转` 疑似应为"给定的轴"。
- `场景.md:20` `// 获取该场景说有物体` 疑似应为"所有物体"。
- 属内容校对范围,不计入"格式偏离"。

## 自动修复可行性

### 完全可自动(脚本级确定修改)
- **Z1. 为整篇内容套一层 ```cs ... ``` 围栏**:8/8 篇适用。启发式:首行检测是否含 `void Start`、`Update`、`MonoBehaviour`、`using UnityEngine`、`Input.*`、C# 关键字 → 整篇包成围栏。
- **Z2. 把文件首行追加 H1 标题(=文件名去后缀)**:8/8 篇适用。`transform控制父子.md` → `# Transform 控制父子` 等。
- **Z3. 追加最小 frontmatter**(只含 `title` 与 `tags: [unity]`):8/8 篇适用。
- **Z4. H3 中的 `_Log_`/`_Find_` 等多余强调符号**:在 Z1 实施后,这些字符自然落在代码块内、不再渲染为强调 —— 这一项事实上被 Z1"自然修复",无须独立处理。
- 合计:**1 类策略**(套围栏 + 补 H1 + 补 frontmatter)同时解决 H1/H2/H3/M1 四个高/中优项。

### 需人工判断(语义/结构决策)
- **Y1. `初步认识.md` 是否转列表/表格**:涉及每行是否作为 `###` 子标题展开。
- **Y2. 多语句挤占行清理**(`场景.md:50`、`游戏物体的获取.md:11`、`触摸.md:38-39`):到底拆成多行还是原样保留,需人核对 Unity 编辑器实际代码风格。
- **Y3. `void Update()` 外的注释重排**(如 M4):属内容校对。

### 不可自动(需保持现状或手工)
- **X1. C# 泛型尖括号** `<BoxCollider>`:在 Obsidian/Markdown 渲染中可能被误解析为 HTML,但本批 8 篇无任何 `<...>` 样式属性,且被围栏后安全。**无需修复**。
